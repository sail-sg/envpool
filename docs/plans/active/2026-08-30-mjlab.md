# Add the complete pinned MJLab task family

This is a living execution plan. Update progress, evidence, and decisions as the
port proceeds; an unchecked milestone is not a claim of supported functionality.

## Purpose / Big Picture

Expose all twelve built-in MJLab task IDs through native EnvPool C++ environments.
Preserve the official observations, rewards, reset distributions, task transitions,
and camera observations. Python is permitted for the oracle and asset generation,
not runtime task logic. Follow the existing new-environment guide, including the
independent randomization checks required by issue #432.

## Surprises & Discoveries

- The official CPU simulation path still calls MuJoCo-Warp. It does not select
  the ordinary C MuJoCo stepper merely because `device="cpu"` is requested.
- RGB, depth, and segmentation observations use MuJoCo-Warp's renderer. A
  successful public OpenGL render alone cannot validate those observations.
- A reset-synchronized Cartpole rollout with identical actions diverges between
  Warp float32 and ordinary C MuJoCo: the state difference is 1.26e-8 after the
  first control step, 1.16e-4 after 100, and 1.12 after 500. Broad tolerances or
  replacing the official oracle stepper would not satisfy the acceptance bar.
- The pinned Warp 1.14 runtime already provides CPU API-capture serialization
  and standalone C++ replay. Investigate that supported upstream interface
  before inventing a custom kernel dispatcher or duplicating the simulator.
- APIC's unqualified closure keys collide across MJWarp specializations, and
  nonzero array fills are not recorded by its CPU memtile implementation. The
  export adapter uses module/symbol identities and records fills as ordinary
  Warp kernels. It does not modify the independent oracle's physics execution.
- Native linkage needs separate namespaces for generated modules, which the
  JIT normally isolates. CPU tile scratch also needs TLS in a multiworker native
  host; the JIT's reserved-register/global-variable scheme is not appropriate.
- Both tracking tasks require a user-supplied motion file. The registered
  default is intentionally empty, and no reference motion is bundled. Preserve
  that input requirement; do not invent a default benchmark or upload to WandB.
- Torch 2.9's official CPU wheels use SLEEF on ARM and Intel MKL VML for several
  unary functions on x64. Matching versions and VML modes are required; SLEEF
  alone does not reproduce x64 sin/cos/exp/log/acos. Static-link probes match
  100,003 inputs per function on Linux and Windows and compress below 0.5 MB.
  Native builds retain no Torch or MKL runtime DLL dependency.
- Torch intentionally uses AVX2, not AVX512, for SumKernel. A 17-length native
  probe matches its sum and squared-sum operations exactly after respecting
  that dispatch boundary. Other kernels still use their own dispatch widths.
- UniformNoiseCfg uses separate rand_like/multiply/add operations. It must not
  reuse Tensor.uniform_'s fused Linux/macOS transform; command resampling does
  use uniform_. Nonbinary curriculum ranges exposed the macOS distinction;
  10,003-input probes exactly match fused transforms for each affected range.
- Torch's ARM scalar cross product contracts a multiply/subtract, while its
  ordinary tensor arithmetic does not. Matching this local behavior removes
  coordinate differences and long-rollout divergence after velocity pushes.
- Reset synchronization must include randomized model fields and their derived
  constants, not only qpos/qvel. A tracking rollout then keeps bitwise physics
  and observations until termination; reward reduction differences remain.
- A complete MJB repeats large mesh BVH arrays across presets. Factoring exact
  array slices at mesh boundaries preserves every byte while sharing flat/rough
  geometry. Generic dictionary compression alone did not remove the repetition.
- The first in-tree Boost JSON consumer exposed stale build metadata: a Python
  GDB helper in the source glob, missing Boost.Compat, and missing direct JSON
  header dependencies. Fix those declarations, not the vendored C++ sources.
- Local free space was 12.3 GiB before installing the oracle. Reuse existing
  build caches and check space before adding substantial builds or wheel sets.
- Warp builds the camera scene BVH before reset, then refits it. Building from
  reset geometry instead changes traversal tie-breaking when a box face and
  a plane have exactly equal ray distance. Preserve the original build bounds
  in exported data; do not mask the resulting RGB difference with a tolerance.
- The pinned viewer copies entire expanded float32 model fields, including
  unmodified elements and derived subtree masses. Updating only randomized
  elements leaves different camera inputs in the host double-precision model.
- Linux's official MuJoCo Python wheel binds MjSpec C++ containers with libc++.
  Substituting a libstdc++ engine invalidates that ABI. Keep the wheel's engine
  on Linux, as the other MuJoCo oracle harnesses already do.
- Windows requires the existing CI MSVC runtime setup for the official Torch
  wheel. Asset generation must explicitly scope capture to CPU even on a GPU
  host. The standalone Warp CRT declarations also need copysign/copysignf for
  MSVC's generated kernel compilation; no physics code or Torch build changes.
- Windows Python can import deep paths with an extended path prefix, but Warp's
  embedded Clang cannot resolve nested includes from that prefix. Map wheel
  imports to Bazel's short physical paths using its runfiles manifest instead.
- A host disk-full incident damaged the ARM guest filesystem and truncated a
  cached libtorch_cpu.so from 252,826,513 to 46,137,344 bytes. Recover the guest,
  verify package RECORD hashes, and restore exact official bytes before using
  that host's validation results. Reuse its existing output base afterward.

- The terrain plane fit uses float32 SSYEVD rather than MuJoCo's double
  eigensolver. Match the official LAPACK backend: Accelerate on macOS, static
  MKL on x64, and the pinned official OpenBLAS plus its Fortran/OpenMP runtime
  on Linux ARM. Only those independent native libraries are redistributed,
  with their complete notices; no Torch library enters the runtime wheel.
- Small covariance products are unfused on x64 and fused on ARM. The larger
  height-scan einsum is fused on Linux/macOS but unfused on Windows. Independent
  point-cloud and 1,001-pose probes isolated these differences before changing
  arithmetic; no broad compiler flag or tolerance was introduced.
- One macOS worker-replay render differed by one level in 24 color channels.
  Thirty standalone replays, eight preceding-shard sequence replays, and three
  full twelve-task render repeats did not reproduce it. Keep exact assertions
  and monitor the final suite instead of adding an unexplained pixel budget.
- Hosted Actions on main are still billing-locked: run 33283834381 reports
  that the job was not started because the account is locked. Native host
  reproductions must not be reported as green hosted checks.

## Decision Log

- Pin one upstream commit and the matching frozen dependency lock. The source
  archive SHA-256 is
  `fc0c7e9d31877b3d921b1f97a5ff0c9a55b3e1d8621e80043f4749048d138c42`.
- Scope is Cartpole (2), Go1/G1 velocity tracking (4), G1 motion tracking (2),
  and Yam manipulation (4). RGB, depth, and segmentation are distinct registered
  tasks. Play configurations and external plugins such as WujiHand do not add
  built-in task IDs.
- Investigate backend differences before implementing a comparison strategy.
  Do not silently change the oracle physics, widen tolerances, or omit cameras.
- Prototype native, ahead-of-time Warp physics and camera execution. Keep the
  official MJLab task logic as the independent Python oracle; a prototype is
  not acceptance until standalone multi-step replay matches it.
- Reconstruct packed MJB/WRP bytes in native memory. The narrow Warp patch adds
  a CPU graph loader that calls the same existing parser; it does not change
  physics, require temporary runtime files, or load generated machine code.
- Keep MJLab's Python 3.12 oracle in a separate pip hub. Use the same Torch 2.9
  source version and official CPU wheels, without downloading CUDA dependencies.

macOS and 2.9.0+cpu on the other hosts).

## Plan of Work

First execute the official environment on CPU and inspect the real model, state,
observation, and camera contracts. Audit robot meshes, textures, and reference
motion inputs independently of the top-level source license. Store repository
rules, asset generation, and any necessary upstream build glue under
`third_party/mjlab/`, with generated registry metadata instead of a copied list.

Implement the native family under `envpool/mujoco/mjlab/`, reusing existing
MuJoCo, rendering, and file libraries where appropriate. Keep task logic localized
and make any necessary shared changes narrow. Add public registrations, package
data, make/release coverage, and a documentation page with render comparisons.
Large runtime data must not push the core wheel over the existing size limit.

## Concrete Steps

From the repository root, use the isolated oracle Python to instantiate all
registered tasks with a small batch. Supply a documented motion fixture for
the two tasks that require one. Record the source and dependency versions,
actual action/observation spaces, and multi-step results in the evidence folder.
The first probe writes `oracle-cpu-cartpole.{json,log}` there.

During implementation run the relevant family Bazel targets, then `make format`,
`make lint`, and the complete `make bazel-test BAZEL_TEST_TARGETS=//...` matrix.
Use `--nocache_test_results` for the final native run. Run `make release-test`
against installed wheels for Python 3.12, 3.13, and 3.14 on Linux x64, Linux
arm64, macOS arm64, and Windows x64. Follow the established host bootstrap and
GL setup; do not substitute an emulated architecture for a native result.

## Validation and Acceptance

Every ID must have public multi-step determinism and default randomization
coverage. Check independent goals, initial state, model properties, and camera
appearance where stochastic; test different seeds, successive resets, and
parallel slots without oracle state synchronization. Tracking fixtures must
exercise multiple motion frames and task transitions.

For alignment, synchronize at most once after reset, then use identical actions
until episode end. Compare observations, rewards, termination/truncation, exposed
state, and reset/multi-step renders. Retain actual logs and XML referenced by
that build's events, not stale files in a shared test directory. Record wheels,
asset inventories, loaded native libraries, and hashes for release validation.
Hosted Actions results must be distinguished from native host reproductions.

## Idempotence and Recovery

Do not modify the historical DMC PR branch or discard another task's files.
Reuse the pinned downloaded archive only after checking its checksum. Temporary
oracle probes belong outside the product source and must not become runtime
dependencies. Preserve failure evidence, and restore any diagnostic mutation
before official validation. Do not merge or publish a release in this task.

## Interfaces and Dependencies

The external contract must retain twelve distinct task IDs and the official
actor/critic/camera observation structure. Training configurations are the
default, including noise, domain randomization, command resampling, and curricula.
Motion data is an explicit input to tracking tasks. Native stepping must not
import or embed MJLab, Torch, or the official Python environment.
